# AquaGuard delivery outcomes

- [x] **Two-MCU measurement and validation:** The ESP8266 reads only outlet flow, calculates flow/volume, and posts authenticated, sequenced wireless samples to the main ESP32 AP; the ESP32 validates fresh outlet data, reads inlet flow, compares only valid samples, and does not turn missing telemetry into a measured zero. Sensor values above the configured 30 L/min bound are rejected/discarded. The main ESP32 is the only relay/valve actuator.
- [x] **Flow-only section estimation:** Use the user's 1 m pipe length and estimated 8–12 mm diameter. With two flow sensors and no pressure sensors, identify at most the instrumented section; do not claim an exact location within it. Return distance-from-inlet as unknown and explain that additional intermediate/acoustic/pressure sensing is required to resolve a point.
- [x] **Nine requested languages:** Support English, Kinyarwanda, French, Kiswahili, Chinese, Dutch, Italian, Spanish, and Hindi. The AI language selector persists the administrator's choice; cloud AI and alert summaries use that locale for dashboard content and subsequent ESP32 SMS/LCD notification polling. SMS uses UCS2 for non-Latin scripts; 16×2 LCD renders a short transliteration where glyphs are unavailable.
- [x] **Local actuation and relay mapping:** Configure the solenoid as normally open when unpowered and route its coil supply through the relay's NO contact. Relay de-energized commands valve-open; relay energized commands valve-closed. Include a separate serial relay-verification sketch and guarded local reset. Show commanded state only because there is no valve-position feedback.
- [x] **SMS, LCD, buzzer and connectivity:** Queue one SMS per cloud alert and warning/critical AI insight; rotate short localized cloud summaries on the LCD; schedule status SMS every 60 seconds; keep local flow/buzzer/LCD behavior without Internet. Pending SMS are persisted/retried across reboot in a bounded 32-entry queue. A cloud-health outage notice is queued after 120 seconds from the first failed probe and a recovery notice on restoration. Carrier receipt/timing and overflow behavior remain hardware/runtime limitations.
- [x] **Independent offline dashboard:** The ESP32 serves its own live local dashboard at `192.168.4.1`, independent of the PC/cloud. It exposes local flow/valve-command/buzzer/cloud state, last alert, SMS status, physical LCD text, language choice and guarded reset. The cloud app offers an offline link and caches its static shell after first visit; fresh Supabase values are not claimed while disconnected.
- [x] **Local/Vercel application and security:** Support `pnpm dev`, `/api` routes and Vercel static output. Validate data before persistence, use dashboard bearer protection, keep service-role credentials server-side, move firmware secrets to ignored local header files, and use verified TLS for HTTPS.
- [x] **Additive data support:** Add internet alert enum values, receipt timestamp/sensor/device health fields, a `NOT VALID` historical 30 L/min check constraint that applies to new readings, and server-only preferred-language settings. Keep migration application as a deployment action; no production database was modified here.
- [x] **Software validation evidence:** Node unit tests pass, JavaScript syntax checks pass, Vercel static build succeeds, and local static/API routes and the route manifest were smoke-tested. These do not establish physical or production behavior.
- [ ] **Apply migrations and configure services:** Apply/verify migrations 001–006 in the intended Supabase project; verify `XXSR69` and its zone; configure local `.env` and/or Vercel `SUPABASE_*`, `ESP32_API_KEY`, `DASHBOARD_ACCESS_TOKEN`, `CRON_SECRET`, thresholds, and optional Telegram settings. Do not create fake production readings.
- [ ] **Install/verify hardware build:** Create private credential headers, flash the main controller and outlet MCU, and confirm startup on the operator's hardware. Source compile checks are run in this release; flashing, board-specific port selection, and runtime behavior still require the operator.
- [ ] **Physical commissioning:** Calibrate inlet/outlet sensor constants independently, confirm flow direction and pulse behavior, verify the ESP32 AP/ESP8266 link, GSM SIM/network/supply, LCD, buzzer, relay NO contact polarity and actual normally-open valve motion with water isolated, then supervised low-pressure operation. A NO valve opens when unpowered; this is not fail-closed on power loss.
- [ ] **Deployment/real delivery verification:** Verify the chosen local PC LAN endpoint or deploy Vercel after database setup; confirm `/api/health`, authenticated dashboard, ESP32 ingestion, Supabase persistence, outage/recovery SMS, per-minute SMS and cloud AI/alert delivery to GSM/LCD. No physical hardware, live carrier, Supabase or Vercel deployment was tested by this task.
